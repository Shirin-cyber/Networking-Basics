## 5.1.1 Communication protocols

People communicate in lots of different ways and places, and we expect different things depending on the situation. Chatting with a friend online isn't the same as sitting in a job interview. Each situation has its own **expected behaviors and styles**.

Before we communicate, we set up **rules or agreements** for the conversation. These are the same three questions from the Module 5 intro:

- What **method** of communication should we use?
- What **language** should we use?
- Do we need to **confirm** that our messages were received?

Those rules are called **protocols**, and they have to be followed for a message to be **delivered and understood**.

### The protocols of human communication

| Protocol | Example |
|---|---|
| **An identified sender and receiver** | Who's talking, and who's listening |
| **An agreed method** | Face-to-face, telephone, letter, photograph |
| **A common language and grammar** | Both people understand what's being said |
| **Speed and timing of delivery** | How fast and when the message arrives |
| **Confirmation or acknowledgment** | Letting the sender know the message was received |

And the big idea: **network communication uses the same fundamentals as human conversation.**

### Try it: texting protocols

The course asks me to think about the commonly accepted protocols for texting friends. Here's my attempt:

| Human protocol | Texting version |
|---|---|
| Sender and receiver | My name and number on one end, my friend's on the other |

## 5.1.2 Why protocols matter

Computers need rules too. Protocols are what let them communicate across a network.

In both **wired and wireless** setups, a **local network** is an area where all the hosts have to **"speak the same language,"** which in computer terms means they **share a common protocol**.

If everyone in a room spoke a different language, nobody could talk to each other. Same with devices: **if they don't use the same protocols, they can't communicate.**

**Connecting the dots:** this is exactly the Kishori and Srinivas story. English was the shared language that let them talk, and a shared protocol does the same job for devices. It also explains 3.1.1, where Bluetooth worked with "different rules and protocols" than Wi-Fi. They're different languages.

### What protocols define

Network protocols cover a bunch of things about local communication:

| Characteristic | What it means |
|---|---|
| **Message format** | A message has to use a **specific format or structure**. The format depends on the **type of message** and the **channel** used to deliver it. |
| **Message size** | The rules for the **size of the pieces** sent across the network are **very strict**, and they can differ by channel. A long message may need to be **broken into smaller pieces** so it can be delivered reliably. |
| **Timing** | Timing sets the **speed bits are sent**, **when a host can send data**, and the **total amount of data** in one transmission. |
| **Encoding** | The sending host turns the message into **bits**. Each bit is **encoded** as a pattern of **sounds, light waves, or electrical impulses**, depending on the media. The destination host **decodes** the signal to understand the message. |
| **Encapsulation** | Every message needs a **header** with **addressing info** that identifies the **source and destination hosts**, or it can't be delivered. **Encapsulation** is adding that info to the pieces of data. The header may also have info to get the message to the **right application** on the destination host. |
| **Message pattern** | Some messages need an **acknowledgment** before the next one is sent. That **request/response pattern** is common. Other messages are just **streamed** across the network without caring whether they arrive. |

### Connecting the dots (this is where a lot of earlier stuff clicks)

- **Encoding** is the bits-to-signals idea from 1.2.3. Bits become **electrical impulses** (copper), **light** (fiber), or **radio waves** (wireless), and the destination converts them back. Now I know the technical word for it.
- **Encapsulation** relates to 2.2.3, where hosts were identified by **addresses**. The addresses go in the **header**. And in 4.3.2, the **SSID is sent in the header of every frame**, so that's a header in action.
- **Timing** sounds related to **bandwidth and throughput** from 1.3, since it affects how fast bits move. I'm guessing the details come later.
- **Message size** means a big message gets split up. I think those pieces get proper names later in the module.
- **Message pattern:** the request/response one is like a **client asking a server for a webpage** (2.1), and the server answering. It's also like Srinivas **signing a document** to confirm he understood. The "streamed with no confirmation" kind is probably something like a live video, but the course doesn't say.

### How the human protocols line up with the network ones

This is my own mapping, so I'll see if the course agrees later:

| Human protocol | Network version |
|---|---|
| Identified sender and receiver | **Encapsulation** (addressing in the header) |
| Agreed method of communicating | The **channel/media**, which affects the **message format** |
| Common language and grammar | **Message format** and **encoding** |
| Speed and timing of delivery | **Timing** and **message size** |
| Confirmation or acknowledgment | **Message pattern** (request/response) |

## What I want to remember

- **Protocols** are the rules for communication. For a message to be delivered and understood, they have to be followed.
- Human protocols (sender and receiver, method, language, timing, acknowledgment) have network equivalents.
- A **local network** works when all hosts **share a common protocol**. Without that, they can't communicate.
- Protocols define **message format, message size, timing, encoding, encapsulation, and message pattern**.
- **Encoding** = bits turned into sounds, light, or electrical impulses, and decoded at the other end.
- **Encapsulation** = adding a **header** with source and destination addressing to the data.
- **Message pattern:** some messages need an acknowledgment (**request/response**), and others are just streamed.
