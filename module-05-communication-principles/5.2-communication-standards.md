## 5.2.1 Video: Devices in a bubble

This video flips the way I think about a network. It starts with how **I** see it, and then asks how the **devices** see it.

### How I see the network

Using **topology diagrams**. They show:

- **End devices** like desktops and servers
- **Intermediary devices** like switches and routers
- Sometimes detailed info about a device, like the **MAC address** of its Ethernet and wireless **NICs**, its **IP address** info, the **default gateway** address, and the **DNS server** addresses

The video says not to worry about those terms yet, because they'll be explained later in the course. I'll just keep a list of them.

### How a device sees the network

It basically **doesn't**. The picture the video uses is that **every device is in its own bubble**. The only thing a device knows is **its own addressing information**.

So that raises a bunch of questions:

- How does a device know its **IP address** and **which network it belongs to**?
- How does it know whether the destination is on the **same network** or **another one**?
- If the destination is on another network and the info has to go through **intermediary devices**, how does it know **where to send it next**?
- How does it know if the info was **received**, or if it has to **resend** something?

The answer to all of them is **protocols**, the rules that govern how devices communicate.

### Packets

Most network communication gets **broken up into smaller pieces**, which the video calls **packets**. And when packets are sent, **lots of protocols** are involved, each doing a different job.

**Connecting the dots:** back in 5.1.2, message size said a long message gets broken into smaller pieces, and I guessed those pieces would get a proper name later. Looks like "packets" is the name.

### Who does what

| Protocol | Its job |
|---|---|
| **Ethernet and wireless protocols** | **Physically connect** a device to the network |
| **DHCP and ICMPv6** | Provide **IP addressing info** (see below) |
| **IP** | **Delivers the packet** from the source to the final destination, like sending a **letter** |
| **TCP** | Guarantees **reliability**: makes sure everything that was sent was received. If any IP packets don't make it, **TCP resends them**. |

And what that IP addressing info includes:

- The **IP address**, which tells the device **what network it belongs to**
- The **default gateway** address, which tells the device **where to send packets going to another network**
- The **DNS server** address, which is for when the device **knows a domain name** but **needs the IP address** of the destination

### Walking through it: loading www.example.com

This is my own walkthrough of the example in the video:

1. The device is connected to the network using **Ethernet or wireless**.
2. It gets its **addressing info** (IP address, default gateway, DNS server) from **DHCP** or **ICMPv6**.
3. I ask for **www.example.com**, so the device asks the **DNS server** for the **IP address** of that domain name.
4. **IP** delivers the packets to the **web server**. Since the server is on another network, they go through the **default gateway**.
5. The web server **responds with the web page**.
6. **TCP** makes sure all the pieces arrive, and **resends** any packets that got lost.

**Connecting the dots:**

- This is 2.1 in action: a **client** requests a page, and a **server** responds. Now I can see the **protocols** working underneath.
- The **default gateway** is the router's address from the Packet Tracer lab in 4.4, and **DHCP** is the same service the router ran to hand out IP addresses.
- **TCP resending lost packets** is the "confirmation" idea from 5.1. It's like Srinivas signing to show he understood. The network version just does it automatically for every piece of data.
- ICMPv6 has a "v6" in it, so I'm guessing it has something to do with **IPv6**, which is on the course goals list.

## 5.2.2 The internet and standards

New devices and technologies keep showing up, so how does the internet keep delivering things like **email** reliably without falling apart? **Internet standards.**

A **standard** is **a set of rules that determines how something must be done.**

Networking and internet standards make sure that **all devices** connecting to the network use the **same rules or protocols in the same way**. That's what allows **different types of devices** to send information to each other over the internet.

**Example:** how an email is **formatted, forwarded, and received** follows a standard. So someone can send an email from a **personal computer**, and someone else can read it on a **mobile phone**, as long as the phone uses the same standards as the computer.

**Connecting the dots:**

- This is the difference between a **protocol** and a **standard**. A protocol is the rules for communicating. A **standard** is when everyone agrees to follow those rules the same way. My guess in the Module 5 README was pretty close.
- It's the same thing as the Wi-Fi Alliance and the Wi-Fi logo from 4.3.1. A router and a phone from different companies work together because they follow the same standard.

## 5.2.3 Network standards organizations

An internet standard isn't just decided by one person. It's the end result of a **long cycle of discussion, problem solving, and testing**. And a lot of **different organizations** develop, publish, and maintain them.

When someone **proposes** a new standard, every stage of the development and approval process is **recorded in a numbered Request for Comments (RFC)** document. That way, how the standard evolved can be tracked.

**RFCs for internet standards** are published and managed by the **Internet Engineering Task Force (IETF)**.

### The organizations I've met so far

| Organization | What it does |
|---|---|
| **IETF** (Internet Engineering Task Force) | Publishes and manages **RFCs** for internet standards |
| **IEEE** (Institute of Electrical and Electronics Engineers) | The main organization creating **wireless technical standards**, like **802.11** (from 4.3.1) |
| **Wi-Fi Alliance** | **Tests** wireless LAN devices from different manufacturers (from 4.3.1) |

## What I want to remember

- A **device doesn't see the network** the way a topology diagram does. It's in its own **bubble** and only knows its own addressing info.
- **Protocols** are how devices figure out their IP address, whether a destination is local or remote, where to send packets next, and whether to resend.
- Messages are broken into **packets**.
- **Ethernet/wireless** connect the device, **DHCP/ICMPv6** give it addressing info, **DNS** finds the IP address for a domain name, **IP** delivers the packets (like a letter), and **TCP** makes sure everything arrives.
- A **standard** is a set of rules that determines how something must be done, so **different devices** can communicate.
- Standards come out of **discussion, problem solving, and testing**, and are tracked in numbered **RFCs**, published and managed by the **IETF**.
